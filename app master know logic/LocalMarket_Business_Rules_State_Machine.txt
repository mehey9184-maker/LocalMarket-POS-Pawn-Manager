LOCALMARKET POS & PAWN MANAGER
BUSINESS RULES & STATE MACHINE
VERSION 1.0 — MASTER LOGIC

PURPOSE

This document defines the authoritative business logic for LocalMarket POS & Pawn Manager.

AI Studio and all application code must treat these rules as the source of truth for business behavior.

Do not invent alternative business rules separately inside screens, components, contexts, API services, database functions, or offline logic.

If an existing implementation conflicts with this document, identify the conflict and change the implementation to follow this document.

The application must prioritize:

1. Correct business transactions
2. Data integrity
3. Auditability
4. Shop isolation
5. Staff authorization
6. Fast cashier operation
7. Safe offline operation
8. Clear recovery from failures

==================================================

1. BUSINESS ENTITY SEPARATION
   ==================================================

LOCALMARKET HAS THREE DISTINCT HUMAN RELATIONSHIPS

A. RETAIL BUYER

A person purchasing goods from the shop.

A retail buyer does NOT automatically become a persistent Customer.

A customer profile may only be created when the person is intentionally identified for an ongoing business relationship such as:

* warranty
* service
* receipt history
* customer relationship
* pawn activity

Entering a phone number during checkout does NOT automatically create a persistent Customer.

B. SELLER

A person selling goods TO the shop.

Seller is a persistent business entity.

Seller history must include, where applicable:

* seller identity
* item
* SKU
* transaction amount
* date/time
* compliance/SAPS reference
* staff member
* shop
* transaction status

A returning Seller must be identified as:

"Previous seller found"

Never call this:

"Customer found"

C. PAWN CUSTOMER

A person entering into an ongoing pawn relationship with the shop.

Pawn customer becomes a persistent Customer because the relationship continues through loans, repayments, extensions and redemption/default events.

2. SHOP AND BRANCH RULES
========================

A staff member may belong to only ONE active shop at a time.

The same employee may later be transferred to another LocalMarket branch.

Historical transactions remain attached to the shop where they occurred.

Owner may have access to multiple shops.

Owner can switch between authorized shops.

Manager belongs to ONE shop only.

Manager cannot manage multiple shops simultaneously.

A staff member must never automatically be assigned to the first active shop.

shop_id must be explicit and authoritative.

Cross-shop business access is forbidden.

All business queries and mutations must be shop scoped.

NORMAL APPLICATION ROLES

6. OFFLINE-FIRST PRINCIPLE
==========================

LOCALMARKET IS LOCAL-FIRST.

The PC must continue operating when internet connectivity is unavailable.

LOCAL PC:

* operational cache
* frequently used inventory
* recent sales
* recent customers
* recent sellers
* shop configuration
* offline transaction queue
* local business records required for operation

SUPABASE:

* authoritative shared cloud database
* cross-terminal state
* business transaction authority
* RLS
* atomic RPCs
* audit records
* synchronization target

BACKBLAZE B2:

* photographs
* files
* binary assets

The application must NEVER display:

"Synced"

unless the remote transaction actually succeeded.

Offline operation may continue for more than 12 hours.

There is NO arbitrary 12-hour shop shutdown.

Instead display:

"Offline — changes will sync automatically"

9. SERIAL / IMEI RULES
======================

Unique serial/IMEI items cannot have duplicate ACTIVE identifiers.

Already SOLD historical records may retain the same serial/IMEI.

MATCH RESULTS

ACTIVE MATCH:

Hard stop.

"This serial/IMEI already belongs to active inventory."

HISTORICAL SOLD MATCH:

Warning.

"This serial/IMEI was previously sold. Verify that this is the same physical item."

PAWN/COMPLIANCE MATCH:

Hard stop and management review.

SERIAL ENTRY

Cashier should NOT be forced to type a serial/IMEI when the value can be reliably obtained through:

* scanner
* device lookup
* existing system source

Manual entry remains available.

NO SERIAL/IMEI

Allow where appropriate.

Require an identification reason such as:

* No serial present
* Serial worn/illegible
* Product does not normally have serial
* Serial could not be electronically detected

Higher-risk categories may require Manager approval.

15. PAWN RULES
==============

If Customer has overdue loan:

Display prominently:

"OVERDUE"

New pawn loan is allowed only with Manager approval.

Cashier may propose valuation/principal.

Cashier cannot independently change calculated interest/fees.

Manager may override within configured limits.

Owner may override with full audit.

PAWN PAYMENTS

Partial payments are allowed.

Every payment is a separate immutable ledger event.

EXTENSIONS

Loan extensions are supported.

Number of permitted extensions is configurable by Owner/shop policy.

Default may be 3.

Every extension creates permanent history.

PAWN HISTORY CANNOT BE DELETED.

17. CONCURRENT INVENTORY EDITS
==============================

Multiple terminals may interact with the same item.

Use concurrency protection.

If Item changes after a user opened it:

"This item changed while you were viewing it."

Do not silently overwrite the newer version.

Two users selling the same unique item:

Only ONE transaction may succeed.

Database must enforce this.

Second transaction must receive an operational message:

"Item LM-000184 was already sold on another terminal."

19. VOID VS REFUND
==================

VOID

A transaction stopped/reversed as part of immediate checkout before becoming a completed sale.

REFUND

A completed sale existed and is subsequently reversed.

Do not treat these as the same event.

20. ATOMIC RETAIL SALES
=======================

When online:

LocalMarket must call the secure atomic retail-sale operation.

Database must atomically:

* verify item availability
* create sale
* update inventory
* enforce shop ownership
* prevent duplicate transaction
* enforce idempotency

A successful UI operation does NOT mean a business transaction succeeded.

==================================================
21. PAYMENT / CRASH RECOVERY
============================

Every sale must have:

* stable UUID
* stable receipt number
* idempotency identity

If browser crashes after payment but before receipt screen:

DO NOT automatically create another sale.

First recover/query the original transaction by its stable transaction ID.

If server already accepted the sale:

restore it locally.

If server did not accept it:

the application may safely attempt the original operation according to retry rules.

Never create a new transaction ID during ambiguous recovery.

==================================================
22. OFFLINE SALES CONFLICTS
===========================

Example:

Cashier A sells Item X offline.

Cashier B sells Item X online.

When Cashier A synchronizes:

DO NOT silently overwrite either transaction.

Create:

CONFLICT — MANAGEMENT REVIEW

Preserve the original records.

Do not simply delete the offline transaction.

Management resolves the business exception.

===================

## Original Sold Amount

# Previously Approved Refund Amount

==================================================
25. REFUND STATES
=================

Pending Approval
→ Approved
→ Payment Pending
→ Refunded

OR

Pending Approval
→ Rejected

A rejected request remains permanently in history.

Resubmission creates a NEW refund request linked to the previous rejected request.

APPROVAL IS NOT THE SAME AS PAYMENT.

Do not mark a refund "paid" merely because Manager approved it.

31. COMPLIANCE / SAPS
=====================

Compliance is part of the acquisition lifecycle.

Applicable regulated acquisitions must have required compliance information before being treated as fully cleared retail stock.

PENDING COMPLIANCE

Allowed state for offline capture where operationally necessary.

Item must not become normally sellable until required compliance is resolved.

FAILED COMPLIANCE

Quarantine.

Compliance records:

* cannot be deleted
* cannot be silently overwritten
* corrections become permanent history/addenda

Every material compliance change must be auditable.

35. AUTHENTICATION AND SESSION
==============================

Supabase authentication uses:

* persistent browser session
* automatic token refresh
* proactive session validation
* token refresh on expiry/near expiry
* single in-flight refresh promise
* retry-once after JWT expiry
* session recovery on browser foreground/focus

If session cannot be recovered:

* safely sign out
* show clear authentication message
* do NOT display fake empty business data
* do NOT delete local business data

==================================================
36. SECURITY
============

Frontend authorization is NOT sufficient.

Sensitive operations must be protected by:

1. UI permission
2. Server authorization where applicable
3. Supabase/RLS
4. Database RPC/business-operation authorization
5. Audit trail

NEVER:

* trust client-provided shop_id
* trust client-provided role
* use first active shop as fallback
* use anon key as service-role substitute
* expose service-role key in browser
* use universal manager PIN
* allow cross-shop business access
* allow cashier to permanently alter controlled pricing
* allow cashier to approve own refund
* allow staff to create Owner/Admin via normal provisioning

==================================================
37. ERROR MESSAGES
==================

Do not expose raw database errors to normal cashiers.

BAD:

23505 duplicate key violation

GOOD:

"Item LM-000184 was already sold on another terminal."

Errors should be:

* clear
* actionable
* human
* operationally accurate

Do not hide real failures.

Do not return an empty business dataset when the underlying cause is authentication failure.

==================================================
38. DATA RECOVERY RULE
======================

Cloud success + local failure:

Cloud remains authoritative.

Recover the accepted cloud transaction into local cache.

Local success + cloud failure:

Transaction remains local/pending according to allowed offline rules.

Cloud conflict:

Preserve transaction.

Mark:

Conflict

Require management resolution.

======================================

Do not implement business state rules independently in:

* individual React components

==================================================
41. DEVELOPMENT RULE
====================

Before adding or changing functionality, AI Studio must ask:

1. Which business entity does this modify?
2. Which shop owns it?
3. Which staff role is allowed?
4. Is the operation online-only, offline-safe, or offline-captured?
5. What is the valid state transition?
6. What happens if it is attempted twice?
7. What happens if the browser crashes?
8. What happens if the network fails?
9. What is recorded in the audit trail?
10. What happens if another terminal changes the record simultaneously?

Do not consider a feature complete until these questions have been addressed for material business operations.

==================================================

==================

When requirements conflict, prioritize:

1. Legal/compliance integrity
2. Data integrity
3. Security/shop isolation
4. Financial correctness
5. Inventory correctness
6. Auditability
7. Offline resilience

9. Visual convenience

==================================================
43. FINAL NON-NEGOTIABLE RULE
=============================

A successful button click is NOT a successful business transaction.

A transaction is successful only when the authoritative business operation has succeeded according to the appropriate online/offline rules.

Every important transaction must be:

* identifiable
* durable
* auditable
* recoverable
* retry-safe
* shop-scoped
* role-authorized
